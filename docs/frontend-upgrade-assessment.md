# 前端技术栈升级可行性评估(JS → TS7 / Vue)

> 评估日期:2026-10-13　代码基线:v1.2.8
> 结论一句话:**TypeScript 值得做但要按阶段推进;Vue 化不推荐 —— 实测数据不支持「切换更丝滑」这个前提。**

本文所有数字都是在真实代码上跑出来的,不是估算。

---

## 一、现状盘点

| 项目 | 实测值 |
| --- | --- |
| 前端源码 | `main.js` 1775 行 + `style.css` 1105 行 + `animations.css` 29 行 |
| 框架 | 无(原生 DOM + `innerHTML` 模板字符串) |
| 构建 | Vite 6.1,零运行时依赖 |
| 产物 | JS 68 KB(min)/ **20.9 KB(gzip)**;CSS 31 KB / 6.3 KB |
| 视图层结构 | 10 个 `render*` 函数、9 处 `innerHTML` 赋值、58 个 `addEventListener`、19 处 `dataset` 事件委托、42 段 HTML 模板 |
| 后端契约 | **Wails 自动生成,且已带完整类型**:`wailsjs/go/main/App.d.ts` + `models.ts`(`Settings`/`Task`/`Snapshot` 字段齐全) |
| 后端方法数 | 约 20 个 |

一个关键事实:**前后端契约的类型定义已经存在且是自动生成的**。这决定了后面所有结论。

## 二、TypeScript 7 可行性验证(实测)

### 2.1 TS7 现状核实

| 项目 | 事实 |
| --- | --- |
| 当前版本 | **typescript 7.0.2**(7.0 于 2026-07-08 GA,7.0.2 为最新补丁) |
| 实现 | 编译器用 **Go 重写**(内部代号 Corsa),`tsc` 现在是原生二进制 |
| 安装体积 | 实际装下来只有 **2 个包**:`typescript` + `@typescript/typescript-win32-x64` |
| 速度 | 官方数据 VS Code 全量检查 125.7s → 10.6s(约 12 倍);本项目实测 **1.66 秒** |
| 破坏性变更 | `strict` 默认开启;`target: es5` 移除;ES2025 默认目标;AMD/UMD 移除;`node10` 模块解析移除 |
| 已知限制 | 面向库/工具链的编程式 API 要到 7.1 才稳定(`typescript-eslint` 等需暂留 6.0) |

### 2.2 「TS7 和 Go 更合得来」——这个判断需要修正

**TS7 用 Go 写,和你的 Go 后端没有任何技术关联。**

- `tsc` 和你的 Go 编译器是两个独立进程,不存在互操作、性能联动或产物互通
- 唯一真实的关联点:Go 侧通过 Wails 生成 `.d.ts`,TS 侧消费它 —— 而这条链路**本来就已经通着了**(实测:与后端契约相关的类型错误 **0 个**)
- 所以「换成 Go 写的 tsc 能配合 Go 后端」是个心理直觉,不是技术收益

### 2.3 迁移成本实测

把 `main.js` 直接改名为 `main.ts`,开 TS7 默认严格模式:

| 阶段 | 错误数 | 做了什么 |
| --- | --- | --- |
| 初始(TS7 默认 strict) | **205** | 只改文件后缀 |
| + `global.d.ts` 声明 Wails 全局对象 | 198 | 约 8 行 |
| + `tasks: Task[]` 类型标注 | **173** | **2 行** |
| + 查询助手收窄 `querySelector` 返回类型 | **153** | 约 5 行 + 批量替换 |

**错误构成(剩余 153 条):**

| 类型 | 数量 | 性质 |
| --- | --- | --- |
| 纯 DOM 事件/元素类型(`EventTarget.closest`、`e.key` 等) | 47 | 机械,加类型参数即可 |
| `querySelector` 可能为空 | 53 | 机械,现有代码本来就在判空 |
| 回调参数隐式 `any` | 33 | 机械,补上下文类型 |
| 「可能为 undefined」 | 33 | **值得逐条看,可能藏着真问题** |

### 2.4 关键判断

1. **205 个错误里有 3 个根因**。`tasks: []` 被推断成 `never[]` 一项就制造了 23 个错误;`Window` 未声明制造了 15 个。修根因比修表象省力得多。
2. **与后端契约相关的错误:0 个**。Wails 生成的 `.d.ts` 开箱即用,这是本项目最大的利好。
3. **但这不是免费的**。153 条错误虽机械,每条都要一个决定,并且 10 个渲染函数改完都要回归验证 UI。「操作一致、UI 不变」的要求意味着**不能靠类型断言糊过去**。
4. **TS 的增量维护收益在这个项目里有限**。核心卖点是「后端字段改名时前端报错」,但 `.d.ts` 是自动生成的,字段改名本来就会同步。真痛点是「拼错 `task.porgress` 这类笔误」—— 这类错误 153 条里能筛出一部分,但收益面不宽。

## 三、Vue 化可行性验证(实测)

### 3.1 技术上能做

Vue 3.5.43 是当前稳定版(3.6 在 RC,引入 Vapor Mode 免虚拟 DOM)。Vite 本就是 Vue 作者的作品,集成无摩擦。

### 3.2 但核心动机不成立

你的理由是「路由切换更加丝滑」。**实测当前切换耗时:**

| 场景 | 实测 |
| --- | --- |
| 页面切换(60 条任务全量重绘,20 次取平均) | **5.28 ms/次** |
| 页面切换(空队列) | 1.08 ms/次 |
| 单行样式更新 | 0.002 ms |
| 切换时的 DOM 规模 | 1672 个节点 / 124 KB |

**5.28 ms 远低于人眼可感阈值**(60Hz 一帧是 16.7 ms)。当前实现已经是全量 `innerHTML` 重绘 —— 这是最笨的渲染方式,而它依然只有 5 毫秒。Vue 的虚拟 DOM 差分要优化的,是一个**已经感知不到的东西**。

### 3.3 体积不是问题,但也不是收益

- Vue 3 runtime-only ≈ **23 KB gzip**;当前整个 JS 才 20.9 KB gzip,加了大约翻倍
- 但这是**桌面应用,资源从本地磁盘加载,不走网络** —— 多这十几 KB 用户完全无感
- 所以「会不会变慢/变大」不是决策依据,**「值不值得重写整个视图层」才是**

### 3.4 重写面与回归风险

要 Vue 化就得搬完这些:

- 42 段 HTML 模板字符串 → SFC `<template>`
- 58 个 `addEventListener` → `v-on` / 事件委托改写
- 19 处 `dataset` 委托 → 组件事件
- 10 个 `render*` 函数 → 组件 + 响应式状态
- 全局 `state` 对象 → `reactive()` 或 Pinia

**而你要求「操作一致、UI 一直、后端逻辑不变」。风险恰恰在这里:**

| 行为 | 当前实现 | Vue 实现 | 风险 |
| --- | --- | --- | --- |
| 输入框状态 | 整页重绘,靠 `scrollReset` 标志位补救 | 响应式自动保留 | 行为**不同**,需重新验证 |
| 焦点管理 | 重绘后手动 `.focus()` | 需 `nextTick` 精确控制 | 易出现焦点丢失 |
| 滚动位置 | 重绘后归零 | 可能被保留 | **可感知的差异** |
| 队列局部更新 | `patchDownloads()` 手动比对 `sig` | 细粒度响应式自动更新 | 行为**不同**,进度动画可能变 |
| XSS 转义 | 手写 `safe()` | `{{ }}` 默认转义、`v-html` 不转义 | 迁移时若照搬 HTML 片段会引入**真实安全回归** |

**结论:Vue 化是一次「必须保证零行为差异」的高风险重写,而收益是一个用户感知不到的 5 毫秒。**

### 3.5 vue-router 在这里没有意义

这是桌面应用,没有 URL 可路由,三个页面(下载/设置/关于)靠 `data-page` 切换。引入 vue-router 属于杀鸡用牛刀。

## 四、结论与建议方案

### 4.1 对三个问题的直接回答

| 问题 | 回答 |
| --- | --- |
| TS7 和 Go 更合得来吗 | **不成立**。编译器语言与你的后端语言无关;真实关联只有 `.d.ts`,而它已经通着 |
| 升级后更易维护吗 | **有限提升**。能抓住字段笔误和空值访问,但 Wails 自动生成的类型已经覆盖了最大的一块;153 条机械错误本身是净成本 |
| 前端能 Vue 化吗 | **能,但不推荐**。实测切换已 5.28 ms,无可感知提升;而重写整个视图层且要保证零行为差异,风险与收益严重倒挂 |

### 4.2 推荐路径(按投入产出排序)

**第一优先:先做零风险的类型基建(约 2 小时)**

不追求 `tsc` 零错误,只拿高价值的那部分:

1. 新增 `src/global.d.ts`,声明 `Window.runtime` / `Window.go` / `__APP_VERSION__`
2. `vite.config.ts` 替代 `.js`,开启类型检查
3. 把 `state.tasks` 等关键状态标注为 `Task[]`(消掉 23 个 `never` 错误)
4. 后端导出结构变化时,至少有一个类型入口可查

产出:编辑器补全 + 后端契约可查。**不碰渲染逻辑,零回归风险。**

**第二优先(可选):完整 TS 迁移(约 1~2 天 + 全面 UI 回归)**

只有在你打算持续扩大前端功能时才值得:

1. 按 §2.3 的顺序消错:先根因(3 处)后表象
2. `querySelector` 统一收窄(`q<T>()` 助手)
3. 逐个 `render*` 函数迁移,每迁一个做一次 UI 截图比对
4. `tsc --noEmit` 挂进 CI

**明确不建议:**

- ❌ Vue 化 / React 化 —— 收益不可感知,风险实在
- ❌ 引入 vue-router —— 桌面应用无 URL 路由
- ❌ 为了「Go 技术栈统一」而升 TS7 —— 动机不成立;若要用 TS,5.x/6.x 与 7.0 在类型能力上等价,7.0 的收益(10 倍速度)对 1.66 秒的检查也没有意义

**但如果你出于长期技术债考虑仍要做**:那么做 TS(阶段化、可回退),**不要做 Vue**。理由是 TS 是纯增量、随时可停;Vue 是一次不可逆的全量重写。
